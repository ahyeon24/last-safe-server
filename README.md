# 막차 세이프 (last-safe-server)

**환승 경로 전체를 보고 "막차를 놓치지 않으려면 언제 출발해야 하는지"를 거꾸로 계산하는 서비스의 백엔드.**
출발지와 목적지를 넣으면 경로의 모든 구간 막차를 따져 최소 출발 시각을 구하고, iOS 로컬 알림으로 알려 주는 것이 목표다.

> 현재 상태: **핵심 계산 로직과 외부 교통 API 연동 일부를 구현한 개발 단계.** REST API, 인증, Redis 캐싱, 배치 작업은 설계만 했고 아직 구현하지 않았다. 배포하지 않았다. 자세한 구분은 아래 [현재 개발 상태](#현재-개발-상태)에 있다.

## 개발 배경

막차를 놓칠 뻔한 경험에서 시작했다. 지도 앱은 "지금 출발하면 몇 시 도착"은 알려 주지만, 지하철과 버스를 갈아타는 경로에서 **어느 구간의 막차가 진짜 병목인지, 늦어도 몇 시에는 나가야 하는지**는 알려 주지 않는다. 앞 구간 막차가 남아 있어도 환승할 버스가 이미 끊겼다면 그 경로는 쓸 수 없다.

## 기술 스택

| 기술 | 역할 |
|---|---|
| Java 21, Spring Boot 4.1 | API 서버 |
| Spring Data JPA, MySQL | 엔티티·저장소 (ERD 기준 엔티티와 Repository 작성) |
| RestClient | 외부 교통 API 호출 |
| JUnit 5, AssertJ, MockRestServiceServer | 계산 로직 단위 테스트, 외부 API 응답 형태 고정 테스트 |
| Redis, Spring Security | **의존성만 추가.** 캐싱·인증 코드는 아직 없음 |

**외부 API**: ODsay(대중교통 경로 탐색), 국토교통부 TAGO(지하철 시간표, 지하철역 검색, 버스 노선·위치), 서울시 버스 정류소 정보, 한국천문연구원 특일 정보

## 주요 구현 기능 (코드와 테스트가 있는 것)

### 1. 막차 역산 알고리즘 — `domain/lasttrain/LastTrainCalculationService`
- 경로를 **목적지에서 출발지 방향으로** 거꾸로 돌면서, 각 교통 구간마다 "그 구간 자체의 막차"와 "다음 구간에 맞추려면 타야 하는 시각" 중 더 이른 쪽을 택한다. 그 결과로 최소 출발 시각과 병목 구간을 구한다.
- 도보 시간은 바로 빼지 않고 모아 뒀다가 다음 교통 구간에서 반영한다. 경로가 도보로 끝나는 경우도 마지막에 반영한다.
- "막차 데이터상 운행 없음(NO_SERVICE)"과 "외부 API 조회 실패(FETCH_ERROR)"를 다른 결과로 구분한다.
- 막차가 모두 끊겼는지는 버퍼(추정 구간 여유 시간)를 적용하기 **전** 시각으로 판정한다.

### 2. 모든 구간을 실제 배차 시각에 맞추기 (스냅) — `TripSnapper`, `SnapResult`, `assembly/AssemblyTripSnapper`
- 역산으로 나온 시각은 계산값일 뿐 그 시각에 실제 차가 있다는 보장이 없다. 그래서 각 구간의 시각이 정해지는 즉시, 앞 구간으로 넘기기 전에 실제 배차 시각으로 맞춘다.
- 처음에는 첫 구간만 맞췄는데, 중간 버스 구간의 계산값이 실제 배차와 달라 최종 결과가 틀어지는 반례를 찾아 전 구간으로 확장했다.
- "시간표 데이터가 없음"과 "시간표는 있는데 기한 안에 탈 차가 없음"을 구분한다. 후자를 전자처럼 처리하면 없는 차를 탈 수 있다고 안내하게 된다.

### 3. 자정 넘김과 요일 판별 — `domain/calendar`
- `OvernightTimeResolver`: 막차가 첫차보다 이른 시각(예: 00:10)이면 다음 날로 계산한다.
- `DayTypeResolver`: 새벽 4시 이전 검색은 전날 운행의 연장으로 보고 전날 요일 기준을 적용한다. 공휴일이면 일요일 기준으로 판별한다. (4시는 확정 근거가 없는 잠정값)

### 4. 서울 외 지역 버스 막차 추정 — `domain/bus`
- TAGO가 노선 전체의 막차(기점 출발)만 주기 때문에, 정류소 좌표 사이의 거리(하버사인)와 평균 속도로 정류소별 막차 통과 시각을 추정한다.
- 심야 운행 기록 수집용 엔티티(`BusPollAttempt`, `BusVehiclePosition`, `BusNodePassage`)와 두 관측 사이의 정류소 통과 시각을 보간하는 로직(`BusNodePassageEstimator`)을 구현했다.

### 5. 외부 API 클라이언트 — `external/`

| 클라이언트 | API | 실제 키로 호출 확인 |
|---|---|---|
| `OdsayRouteSearchClient` | ODsay 경로 탐색 | ✅ |
| `TagoSubwayStationLookupClient` | TAGO 지하철역 키워드 검색 | ✅ |
| `TagoSubwayScheduleClient` | TAGO 지하철역별 시간표 | ❌ 공식 활용가이드 기준 구현 |
| `TagoBusLastDepartureClient` | TAGO 버스 노선 막차·경유 정류소 | ❌ 공식 활용가이드 기준 구현 |
| `TagoBusPositionClient` | TAGO 버스 위치 | ❌ 공식 활용가이드 기준 구현 |

- ODsay가 주는 역 ID는 TAGO와 체계가 달라서, 역명과 노선명으로 TAGO 역 ID를 다시 찾는 `SubwayStationIdResolver`를 만들었다. 같은 이름의 역이 다른 도시에도 있어 구분할 수 없으면 억지로 고르지 않고 빈 값을 돌려준다(예: 서울과 대구의 "시청" 1호선).
- 공휴일(`HolidayClient`)과 서울시 버스 클라이언트는 인터페이스만 있고 구현체는 없다.

### 6. 테스트
- 74개, 모두 통과. 대표: `LastTrainCalculationServiceTest`(16개, 설계서의 검증 예시와 과거 버그 재발 방지), `SubwayStationIdResolverTest`, `OvernightTimeResolverTest`, `DayTypeResolverTest`, 외부 클라이언트 테스트(MockRestServiceServer).
- ODsay 테스트 데이터는 실제 응답과 **구조만 같은 가상 데이터**다(이용약관 때문, 아래 참고).

## 시스템 구조 (설계 기준)

```
iOS 앱 ── POST /routes/search ──▶ API 서버
                                   ├─ ODsay 경로 탐색 (실시간 호출 + Redis 캐시 예정)
                                   ├─ 조립 계층: 구간마다 SUBWAY / 서울 버스 / 경기 버스 데이터 소스 선택
                                   │     ├─ TAGO 지하철 시간표
                                   │     ├─ 서울시 버스 막차 (배치 적재 예정)
                                   │     └─ TAGO 버스 막차 추정 → 심야 운행 기록(배치 수집 예정)
                                   └─ 막차 역산 + 스냅 → 최소 출발 시각, 병목 구간
iOS 앱 ◀── 후보 목록 / 알람 등록 → 서버는 DB 저장, 알림은 iOS 로컬 알림으로 예약
```

- 패키지: `domain/`(순수 계산 로직), `external/`(외부 API, 인터페이스로 분리), `assembly/`(구간별 데이터 소스 선택), `entity/`, `repository/`
- 계산 로직(`LastTrainCalculationService`)은 외부 API 타입을 모른다. 어떤 데이터 소스를 쓸지는 조립 계층 한 곳에서만 정한다.

## 기술적 의사결정

| 결정 | 이유 |
|---|---|
| 서버 푸시(APNs) 대신 **iOS 로컬 알림만** 사용 | 알림 시각이 계산 시점에 정해지므로 서버 푸시·토큰 관리·재시도가 필요 없다 |
| ODsay 결과를 **배치로 DB에 쌓지 않음** | 이용약관 제4.5.10조(사전 동의 없는 결과 데이터 저장·배포 금지)와 정확도 문제. 실시간 호출 + 짧은 캐시로 설계 |
| 지하철 막차 데이터 소스를 세 번 바꿈 (ODsay → 서울교통공사 → TAGO) | TAGO가 요일·상하행을 직접 지원하고, 공식 활용가이드 문서로 파라미터를 확인할 수 있었다 |
| 서울시 버스·TAGO 버스는 실시간 호출 대신 **배치 적재**로 설계 | 서울시 API는 "오늘" 값만 주고 요일 지정이 안 되며, TAGO는 타임아웃이 잦다 |
| 요일 정보는 `day_type`으로 뭉개지 않고 **요일·공휴일 원본을 저장**하도록 설계 | 나중에 "공휴일이 정말 일요일 시간표와 같은지" 원본으로 다시 검증할 수 있게 |
| 경로 후보는 `candidate_id`로 서버 캐시에서 다시 꺼내도록 설계 | 알람 등록 때 클라이언트가 보낸 계산값을 그대로 믿지 않기 위해 |
| 버스 심야 운행 수집은 전국이 아니라 **서울·경기 핵심 노선만** | 실사용 이력이 없는 상태에서 전국 수집은 비용만 크다 |

## 현재 개발 상태

| 구분 | 항목 |
|---|---|
| ✅ 구현 + 테스트 | 막차 역산, 전 구간 스냅, 자정 넘김·요일 판별, 버스 막차 추정, 정류소 통과 보간, ODsay 경로 탐색, TAGO 지하철역 검색·ID 재매핑, JPA 엔티티·Repository |
| 🟡 구현했지만 실제 호출 미확인 | TAGO 지하철 시간표, TAGO 버스 막차·위치 클라이언트 |
| ⬜ 설계만 함 (코드 없음) | **Redis 캐싱**(막차 시각 캐시·candidate 캐시), **배치 작업**(서울시 버스 막차 적재, 버스 위치 폴링 스케줄러, 공휴일 갱신, 통계 집계), 조립 계층에서 실제 경로 → 구간 데이터 연결, 공휴일·서울시 버스 클라이언트 |
| ⬜ 미착수 | REST API(컨트롤러), 소셜 로그인·토큰, 알람·즐겨찾기 API, iOS 앱, 배포 |

출시 전에 확인할 것: ODsay에 일시 캐싱이 약관상 허용되는지 서면 문의, 개인정보처리방침, 위치기반서비스 사업자 신고 여부.

## 실행

```bash
./gradlew test     # 테스트 (로컬 MySQL 필요: contextLoads)
```

외부 API 키는 환경변수 `ODSAY_API_KEY`, `DATAGOKR_SERVICE_KEY`로 받는다. 코드와 저장소에 키를 넣지 않는다.
